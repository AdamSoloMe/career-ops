<objective>
Extend the autonomous prep flow so qualified jobs produce complete per-job application packets and three reviewable resume variants. The batch worker should emit enough structured data for packet assembly, a new packet utility should create manifests under `reports/`, and the queue should carry packet references plus a user-facing daily review limit.

Purpose: This plan turns the queue from "eligible jobs" into a real high-throughput approval surface where the user can review a bounded number of prepared application packets each day without losing the no-auto-submit guarantee.

Output: updated batch worker prompt, packet assembly utility, runner integration, and docs covering packet/review behavior.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Batch worker output → packet manifest | The packet utility trusts structured worker output; malformed variant paths could create broken or misleading application packets |
| Packet manifest → user review decision | The packet is the final automation surface before human action, so it must clearly preserve the no-auto-submit boundary |
| Configured daily review cap → user workflow | A bad cap or missing cap can turn "balanced" review into unbounded queue growth or hidden starvation |

## Threats / Failure Modes

| ID | Type | Risk | Mitigation |
|----|------|------|------------|
| T-03-05 | Integrity | Packet manifests point to missing report or variant files | Assemble packets only from structured worker output and write explicit variant/report paths into `packet.md` |
| T-03-06 | Safety | The packet/review layer drifts into automatic application submission | Hardcode manual next-step language and keep docs/scripts scoped to packet creation only |
| T-03-07 | Resource exhaustion | Three variants per role create excessive artifact churn | Generate variants only after queue gate passes and keep the upstream batch cap intact |
| T-03-08 | Usability | Daily review cap is confused with batch cap, leading to over-prep or under-review | Keep separate config keys and document them distinctly |
</threat_model>
